# 从审阅记录生成批注和函评

申请人会收到两份 Word。批注副本用来逐句改，模拟函评给出评价和可逐条核对的清单。同一问题在两份文件中沿用同一编号。少量节选只评有关内容，在对话中用同样的表头给出已审项。

## 评阅输入

整稿使用 UTF-8 JSON。在通读稿件后填写；脚本负责校验和排版，学术判断由评阅者作出。

| 字段 | 写法 |
|---|---|
| `title`、`context` | 实际题名及稿件版本、年度、类别。引用具体文件或附件时先核对版本。 |
| `overall_grade`、`overall_funding` | 综合评价选四档之一：优、良、中、差。资助意见输入 `A`、`B` 或 `C`，分别显示为优先资助、可资助、不予资助。两项分别判断。 |
| `summary` | 直接解释这一对总体结论。聚焦最有价值的科学问题和最影响资助意见的事实。 |
| `panels` | 填五份独立的模拟评语。首页评分表和正文按输入顺序显示“专家一”至“专家五”。不需要填写姓名、单位或专业方向。 |
| `issues` | 需要落在原稿上的问题，见下例。没有可定位的问题时用空数组。 |
| `checklist` | 每个适用模块按行填写。整稿按 A–H、X 填满 70 个基础编号，每条只出现一次；另列实际命中的方法专项 M01–M08。 |
| `rechecks` | 二轮复查时按需提供。每项包括 `id, status, location, note`，写清修订处和复查结论。 |

每个 `panels` 元素填写 `grade, funding, opinions, issue_ids`。前两项分别是综合评价和资助意见字母。`opinions` 是四段中文评语的数组，按下列顺序填写。编辑人员的内部视角标记（如 `perspective`）不参与排序或显示。正文、摘要、表格和批注也不要写“作为某专业专家”等自我介绍。

1. 经济社会发展需要或国家需求背后是哪一个基础科学问题，依据是什么。
2. 科学问题有何创新，预期成果能带来什么科学价值。
3. 申请人的创新潜力和研究方案的可行性，哪项具体改动最有帮助。
4. 其他建议。确无补充时写“无其他建议”。

五位同行可以形成相同或不同的资助意见。第一问先交代真实的管理决策、涉及的主体和未解决的规律；临床场景、患者结局与护理经验可以作证据，题名和评语应回到项目实际研究的管理问题。涉及学科资助范围时先核对[年度依据](annual-rules.md)。

**五份意见分别回到原稿。** 拟定评语时可根据课题选择或随机组合合理的阅读视角，不设专业配额。可从服务覆盖、政策比较、优先分派、班次交接或用药信息记录等处切入，也可围绕同一发现提出不同解释。保留与本稿有实质关联的证据。评语用判断和理由表现差异，报告中不附视角名或方向标签。

前三问把判断写透。有争议的地方可用两段，第一段说清稿中的具体做法和依据，第二段解释它如何影响本人的资助意见，提出一项能解决问题的改动。用“如果两家中心按同一份记录排出不同的优先次序，试验比较的还是同一种策略吗？”这样的具体追问表达分歧。第四问只补前面未说过的建议。不要换个署名就复述同一组优缺点，不设字数配额，也不虚构个人经历。每人仅关联实际用到的批注编号。完整题干由导出器印出；在同一答项内用换行分段即可。

## 表格和批注的颗粒度

下面是同一合成问题的两条记录，分别加入 `checklist` 与 `issues`。

```json
{
  "rule": "F05",
  "status": "需修改",
  "location": "方法 §3.2、年度计划 §2",
  "evidence": "开发组 640 人，验证组写开发人数的 25%；两中心计划各招 112 人。",
  "action": "确认验证组采用 160 人还是 224 人，同步修改两处。",
  "issue_ids": ["F05-01"]
}
```

```json
{
  "id": "F05-01", "status": "需修改", "severity": "局部问题", "basis": "研究方法判断",
  "location": "方法 §3.2，另见年度计划 §2",
  "anchor": {"quote": "验证组按开发组的25%安排"},
  "comment": "按开发组 640 人的 25% 计算，验证组应为 160 人；年度计划却是两中心合计 224 人。请确认实际招募数并统一两处。",
  "problem": "验证比例和计划招募人数不符。", "impact": "两中心无法分配一致的名额。",
  "action": "确认人数与分母，同步年度计划。", "done": "两处的分母、人数和合计均能复算。"
}
```

- `rule` 填清单条号，中文名称由规则库提供。`status` 取通过、需修改、待核实或不适用。每行的 `evidence` 写稿件的具体事实；不适用项说明原因，例如青年 C 包干制项目的预算编报项。`action` 写动作，对通过或不适用项可留空。用 `issue_ids` 将重复根因连回同一条批注，无批注时用空数组。不得用“基本合理，建议完善”等文字批量填表。
- `id` 在主规则后加实例序号，如 F05-01。保留 `problem/impact/action/done` 供判断和复查，申请人看到的是编号和 `comment` 中的一两句同行意见。每次新评都填写 `comment`，避免把内部字段逐一打印出来。依据可取年度官方要求、研究方法判断、团队写作经验；年度硬性规则另填 `source`，写清年份、出处和链接。影响程度分关键、重要、局部。
- Word 的 `anchor.quote` 须为原句中的精确文字；多个段落相同可加 `paragraph`，用下面的命令取段号。同段有多个相同短语时延长短引。图形和复杂域可就近锚定图题或正文，写明实际位置。PDF 需提供从封面起算的 `page` 和 `quote`。扫描页须先目视核字，仅在文本层失真时使用 `visual_verified: true` 并附页图。
- 复查沿用旧编号。已解决项只入 `rechecks`；部分解决或仍待处理的继续在新稿定位。材料缺失时可标待核实，注明所缺资料。保留来稿中原有的历史批注。

## 导出与验收

用工作区提供的 Python（python-docx 1.2 系列与 lxml）。PDF 另需 pypdfium2，扫描页预览使用 Pillow。从技能目录运行：

```text
python scripts/export_review.py --list-paragraphs 原稿.docx
python scripts/export_review.py 原稿.docx 审阅.json 评价_新版
python scripts/export_review.py 原稿.pdf 审阅.json 评价_PDF版
```

目标父目录须存在，输出目录使用新名称。打开 Word 确认批注锚在相应文字，函评首页总评下有五位匿名专家的两项结论，正文共五组、每组四问；翻看各模块表格是否有具体依据、跨页表头和相应编号。PDF 交付物注明为摘录批注本。

新生成的函评报告、检查表及 PDF 摘录本统一用宋体，覆盖标题、正文、表头、单元格、编号、英文和数字。标题层级通过字号、间距和加粗来区分。申请书 Word 副本沿用原稿版式，新增批注文字使用宋体。交付时抽查评分表、五位专家评语、检查表以及批注，确认字体和分页。

仅复现已有三人版 JSON 时使用 `python scripts/export_review.py --legacy 原稿.docx 旧审阅.json 评价_旧版复现`，保留历史人数、身份和原评语。三人旧稿若需五人新评，应先重新审稿补全五份独立意见，再走默认导出。
